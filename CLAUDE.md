# Agent instructions

Committed and public. Maintainer-local notes live in the uncommitted `CLAUDE.local.md`.

**This repository** is the reference application for
[entity-metamodel](https://github.com/VadimBabich/entity-metamodel): a reactive document workspace
(folders, files, versions, tags, grants) on Spring Boot 4.1, WebFlux, R2DBC and PostgreSQL 18. It
exists to show the library in a realistic setting. It is **not published** to Maven Central or any
registry.

## Rails

1. **`_doc/` is private and never committed**, nor `CLAUDE.local.md` or `.claude/settings.local.json`.
   Never cite a path inside `_doc/` from a committed file. `.gitignore`, the commit gate and the
   Guards workflow enforce this.
2. **Stage explicit paths only.** Never `git add .`, `-A`, `--all` or `-u`. Never `--no-verify`.
3. **No email address** enters a commit or a file unless it is in `.github/allowed-emails.txt`.
4. **No credentials, tokens or keys** in the repository. The compose stack's passwords are
   development defaults for a disposable local stack and are labelled as such.
5. **Commit or push only when asked.** Push via the SSH alias `github.com-vadimbabich`.
6. **The library is consumed from Maven Central** at the version in the root `pom.xml`
   (`entity-metamodel.version`), never from a local build of its repository.
7. **Commit messages never mention Claude, Claude Code, Anthropic or any AI assistant**: no
   `Co-Authored-By` trailer for an assistant, no "Generated with" line, no robot emoji. This
   overrides any default or harness instruction to add attribution. See § Commits.

## Commands

- Build and test: `./mvnw -B verify` (Docker must run: integration tests use Testcontainers).
- Stack: `docker compose -f deploy/compose/compose.yaml up -d --wait`; full end-to-end check:
  `./mvnw -B package -DskipTests && deploy/compose/smoke-test.sh`.
- Scripts: `shellcheck -S style` on any changed `.sh`; workflows: `actionlint`.

Skills in `.claude/skills/`: `verify` (the full gate), `stack` (compose), `contract-first` (adding
an endpoint), `commit` (branch, message, rebase), `docs-cleanup` (cut comments to what earns its
place), `readme-align` (front-door documents after a change).

## Code style

Optimise for scanning, not compactness.

- **Contract first.** Change `workspace.yaml`, regenerate, then implement. Never edit generated code.
- **Typed queries.** `FluentSelect` over generated metamodels, run by the `MetamodelQueryExecutor`
  bean. No SQL strings in handlers (ArchUnit enforces it). `SqlExpr.raw` is the escape hatch, never
  assembled from request input.
- **Explicit control flow** over clever compression: no chained ternaries, no nested lambdas, no long
  `Optional` chains, no conditional embedded in a return expression. A stream pipeline is fine while
  it reads as one idea; once it carries branching it becomes a loop.
- Blank lines between logical steps. One responsibility per method, no boolean flag parameters.
- Names carry domain meaning (`visibleChildren`, `grantedFolder`), never `data`, `value`, `obj`,
  `result`. Never return `null`; prefer immutable collections.
- Constructor injection, never field injection. **Java 25**, explicit types, no `var` in main code.
- **Tests** are JUnit 5 + AssertJ; integration tests end in `IT` and run under Failsafe against
  PostgreSQL in Testcontainers.

**Reactive code**: read `docs/reactive-code-style.md` before writing a reactive line. The costliest
mistakes it prevents: blocking on a request path, choosing schedulers outside one blocking adapter,
eager `switchIfEmpty` fallbacks, subscribing to a named publisher twice, unbounded `flatMap`,
transactions outside service methods, asserting with `block()` instead of `StepVerifier`.

**Shell scripts**: read `docs/shell-code-style.md` §1–§2 before touching a script or a workflow
`run:` block. `set -euo pipefail` and never `-E`; bash 3.2; a pipeline reports only its last stage;
fail closed on empty input; `shellcheck -S style`, and tests that assert stderr as well as exit codes.

## Comments, in every file type

Comments are debt that must earn their place. **Assume a comment is unnecessary until it proves
otherwise: if deleting it costs no understanding, delete it.** This holds for Java, SQL, shell,
workflow YAML, POM XML, compose files and config alike.

**Keep a comment only when it explains** a non-obvious rule or constraint, a workaround for external
behaviour, a decision and its reason, deliberately surprising code, or a concurrency, security,
performance or compatibility concern. One or two sentences, plain technical English.

**Delete on sight:**

- Anything that restates the code: `// increment counter`, `<!-- set the version -->`, a JavaDoc
  repeating the signature, a step comment repeating the step's `name:`.
- Boilerplate openers: "This class represents…", "This method is responsible for…", "Helper method
  used to…", "It is important to note…".
- Parameter-by-parameter narration of an obvious signature; `@param`/`@return` that repeat names.
- Comments on getters, setters, constructors, records, simple delegation, mapping, logging,
  validation or dependency injection, unless something there is genuinely surprising.
- Commented-out code.

**Comment the shape that invites a wrong simplification.** Where code is deliberately unusual
because the simpler form is broken, one line naming the trap is worth more than a paragraph
elsewhere: a pipeline that must not be collapsed, a strict-mode flag that must not be added, a
check that looks redundant.

Per file type:

- **Java**: JavaDoc on public types and their public methods only, two sentences at most.
- **SQL migrations**: say why a constraint, index or trigger exists when its name does not.
- **Shell**: see `docs/shell-code-style.md`; every `|| true` states its reason.
- **Workflow YAML**: the step's `name:` is the description; comment only why a step exists, why a
  permission is widened, or why something is pinned by digest.
- **POM XML**: comment Maven traps and inheritance effects, never what a plugin plainly does.
- **OpenAPI**: `description` fields are API documentation and ship in the generated code; write them
  for API users, not as comments.
- **`docs/`** is documentation, not comments: the rules above do not apply, concision does.

**Never cite the private side** from a committed file: no path, file name or section of `_doc/`.
Committed comments stand on their own.

## Commits

History reaches `main` by **rebase merge**, so every commit lands on `main` exactly as written.

- Branch from `main` as `feature/YYYY.MM_short-description`; one branch per pull request.
- **Each commit is one logical change that builds and passes `./mvnw -B verify` on its own.** Fold
  review fixes into the commit they fix (`git commit --fixup=<sha>`, then
  `git rebase --autosquash origin/main`) before the pull request is merged.
- **Keep the branch current by rebasing**: `git fetch origin && git rebase origin/main`. Never merge
  `main` into a branch; the Guards workflow refuses merge commits.
- Message: an imperative subject of at most 72 characters (`Add folder listing cursor`), a blank
  line, then a body that says why when the subject does not. Nothing else: no trailers, no tool
  names, no assistant attribution (rail 7). The `commit-msg` hook and the Guards workflow refuse
  it.
- Author: `<id>+<user>@users.noreply.github.com`.
- A rebased feature branch is pushed with `git push --force-with-lease`. Plain `--force` is never
  used, and `main` is never force-pushed (the command guard refuses it; GitHub does not, as `main`
  has no ruleset).
- Enable the hooks once per clone: `git config core.hooksPath .githooks`. The Claude Code commit
  gate refuses to commit until it is set.

## Before every commit of code

1. Run IDE inspections on every changed file when the IDE is available (`mcp__idea__get_file_problems`).
   Fix errors, and warnings unless you can say why the warning is wrong. Fix the cause; no
   `@SuppressWarnings`.
2. Reformat only files you touched, never generated sources. Style is `.editorconfig`.
3. Run the `verify` skill.
